# Microphone profiles

Phone microphones are not flat. AutoVybz subtracts a microphone response from every measurement. The data
lives in [`app/src/main/assets/autovybz/mic_profiles.json`](../app/src/main/assets/autovybz/mic_profiles.json).

> **Important:** all built-in curves are **estimated archetypes** of typical MEMS bottom-port microphones,
> not lab measurements of the listed devices. They are better than nothing, but a real calibrated
> measurement (or a USB measurement mic in the Pro area) is always more accurate.

## Structure

```jsonc
{
  "schemaVersion": 1,
  "units": { "frequency": "Hz", "level": "dB relative to 1 kHz (what the mic adds)" },
  "default": "mems-bottom-port",            // archetype used for unknown devices
  "archetypes": {
    "mems-bottom-port": {
      "label": "Generic MEMS bottom-port microphone",
      "curves": {                            // one curve per Android input source
        "UNPROCESSED":       [[20, -5.0], [100, -0.1], [1000, 0.0], [10000, 2.8], [20000, -3.5]],
        "VOICE_RECOGNITION": [[20, -14.0], [200, 0.0], [1000, 0.0]]
      }
    }
  },
  "devices": [
    {
      "id": "samsung-galaxy-s-legacy",
      "manufacturer": "samsung",             // compared with Build.MANUFACTURER (normalised)
      "models": ["SM-G9[5-8]\\d.*"],         // regexes on Build.MODEL, case-insensitive; [] = all models
      "label": "Samsung Galaxy S8-S20 series",
      "curveRef": "mems-bottom-port",        // or an inline "curves" object
      "confidence": "estimated"              // measured | community | estimated
    }
  ]
}
```

Archetypes shipped (the acoustic design classes the device entries map to). The curves are not
hand-drawn: the generator computes them from a small physical model of the microphone path —
capsule/ASIC high-pass + Helmholtz resonance of the acoustic port (housing hole + gasket + PCB
neck over the front cavity) + post-resonance HF roll-off — evaluated on the ISO third-octave
grid. Resonance frequencies follow the port-geometry simulations in STMicroelectronics AN4427
(channel length 0.5–4 mm → ≈ 40–13 kHz, widened cavities down to ≈ 7.5 kHz); peak heights and
the low/high-frequency behaviour are centred on published smartphone-microphone population
measurements (≈ ±3 dB from 100 Hz–10 kHz, LF roll-off below ~100 Hz, largely flat to ~20 kHz
when the port is well designed). Processed input sources add the typical HAL voice high-pass
(cascaded 52 Hz / 82 Hz corners for `VOICE_RECOGNITION` / `MIC`).

| archetype | design class | port resonance | LF corner |
| --- | --- | --- | --- |
| `mems-bottom-port` | typical MEMS bottom port (the default for unknown devices) | ≈ +2.8 dB @ 12.5 kHz | 30 Hz |
| `mems-bottom-port-strong-resonance` | narrow/long acoustic channel (many budget phones, foldables) | ≈ +4.9 dB @ 10.5 kHz | 30 Hz |
| `mems-bottom-port-flat` | short/wide channel, well-tuned (most flagships) | ≈ +1.2 dB @ 15 kHz | 16 Hz |
| `mems-bottom-port-damped` | port behind mesh / deeply recessed — no peak, HF roll-off (rugged phones) | — (−10 dB @ 20 kHz) | 30 Hz |
| `mems-early-resonance` | long acoustic channel / big cavity (tablets, thick slabs) | ≈ +3.0 dB @ 7.5 kHz | 30 Hz |

Levels are interpolated logarithmically between the points and normalised to 0 dB at 1 kHz. The curve for
the input source actually obtained (`UNPROCESSED`, otherwise `VOICE_RECOGNITION`, otherwise `MIC`) is used.

## Device coverage

The database is generated by [`tools/micdb/generate_mic_profiles.py`](../tools/micdb/generate_mic_profiles.py)
(edit there, never edit the JSON by hand — CI regenerates it and fails on drift). It holds ~190 device/series
entries for 50+ manufacturers (Samsung, Google, Xiaomi/Redmi/POCO, OnePlus/OPPO/realme, vivo/iQOO, Motorola,
Sony, Huawei/HONOR, ASUS, Nothing, Nokia/HMD, Lenovo, ZTE/nubia, TECNO/Infinix/itel, TCL, the Japanese makers,
the rugged specialists, tablets, …). Matching is manufacturer-first (with normalisation for the raw strings
phones actually report, e.g. "TECNO MOBILE LIMITED"), then model — `Build.MODEL` is a marketing name on some
brands and a model code on others, and the patterns cover both. Every covered manufacturer also has a
model-less fallback entry, and anything unknown gets `mems-bottom-port`, so every phone ends up with a
reasonable correction. Each entry lists example model strings; the generator's built-in routing self-test
proves every entry is reachable and nothing is shadowed by an earlier, broader entry.

## Pro: USB measurement microphone

In the Pro area you can load a calibration file in the common UMIK/miniDSP text format (frequency, dB,
optional phase; a `Sens Factor` header is read) or enter a manual offset profile. That calibration
replaces the phone profile.

## Contributing a measured profile

1. Measure the phone microphone against a calibrated reference mic (same position, same stimulus) –
   ideally outdoors or in a large room with gating to avoid reflections.
2. Add the entry in `tools/micdb/generate_mic_profiles.py` (inline `curves` for `UNPROCESSED`, and
   `VOICE_RECOGNITION` if available; `"confidence": "measured"` and a `notes` field describing the setup),
   regenerate, and make sure the routing self-test passes.
3. Open a pull request. `./gradlew testDebugUnitTest` validates that the database still parses and routes.
